## 安全中心「省电与电池」柔光适配（R8 压缩 apk 的结构发现）

用户反馈：加载安全服务 apk，省电与电池页有多张卡片，**颜色已能改、柔光上不去**。
jadx 反查根因（重要结论）：

1. **分组装饰器被 R8 改名**：MIUIX 内部类/方法在安全中心里成短名——
   `miuix.recyclerview.card.CardItemDecoration` → `miuix.recyclerview.card.f`（`C13600f`）、
   `PreferenceFragment$FrameDecoration` → `PreferenceFragment$f`（`C13532f`）、
   每帧绘制 `calculateGroupRectAndDraw` → `mo44927f`、裁剪 `clipDrawableRoundRect` → `g`、
   drawable 字段 `mGroupDrawable` → `f41500p` / `mCardGroupBackground` → `f40800s`。
   **公开名 `miuix.preference.PreferenceFragment` 与 `androidx.recyclerview...RecyclerView` 都保留。**
2. **颜色能改、柔光不能的原因**：`useGlass`/`useFrost` 都要求 `groupClipAvailable`，
   而它靠按字面名 `loadClass` + 找 `(Canvas,RectF,Path,Drawable)` 裁剪方法；
   压缩 apk 里类名不存在 → 抛异常 → 静默 false → 玻璃分支永久禁用。纯色分支不依赖它，所以颜色一直好使。
3. **省电与电池的自绘卡片**：`pc_battery_fragment_viewstub.xml` 用 `LinearLayout` +
   `selector_battery_card_bg` → `hp_card_bg_no_shadow_normal`（layer-list：全宽底 + 圆角半透明卡色），
   是**独立卡片**不是分组装饰；老的通用判定只读最外层 drawable → 拿不到圆角与填充 → 整片漏掉。

## DexKit 动态匹配方案评估（用户提议，结论：值得加，但只用于「发现」）

用户提出：不要按名字/签名匹配，改为用 DexKit 按「方法体里有什么（返回、参数、引用）」动态匹配。评估结论：**方向正确，且对多 apk/多页面/多组件比纯运行时反射更稳；但它是补强不是替代。**

### 概念澄清（写进文档时要保留）
- 目标实现本身就是 R8 之后的产物，**必须 hook 它**；不能做的是**用 R8 后的名字去认它**。
- R8 还会**内联**小方法 → 按名字找的目标可能根本不在 dex。DexKit 搜的是「最终 dex 里真实存在、且语义匹配的那个方法」，正好绕开内联。

### DexKit 2.x 能力（已核实）
`MethodMatcher`：`returnType`、`paramTypes`/`parameterTypes`、`modifiers`、`declaredClass`、`name`、`usingStrings`、`usingNumbers`、`usingTypes`、`usingFields`、`invokeMethods`（调用了哪些方法）、`annotations`。
`ClassMatcher`：`searchPackages`/`excludePackages`、`fields`(FieldsMatcher, addForType/count)、`methods`(MethodsMatcher, add/count)、`usingStrings`、`annotations`。
性能：链式 `findClass{...}.findMethod{...}` 比 `declaredClass` 条件快数十倍（官方性能指南）；避免在大 dex 上用 declaredClass。
关键：**锚点要用 framework 引用**（`android.graphics.Canvas#saveLayer`/`saveLayerAlpha`、`Path#addRoundRect`、`androidx.recyclerview.widget.RecyclerView$ItemDecoration`），这类名字 R8 不会改；用 app 类型名做 paramTypes 等于又回到名字依赖。

## 「接管全部跟随主题的面」（用户要求：全部背景，含按钮 / card / 徽标）

用户诉求：**「只要有读取深浅色模式的背景，统统替换掉，包括按钮，card，徽标等等」**。

### 关键洞察（这是本轮最重要的设计结论）
用户这句话里的限定词「**只要读取深浅色模式的**」本身就是安全阀——它自动排除了
红点、品牌色按钮、图标、图片，而这些正是「全部替换」最容易搞坏的东西。
所以不需要枚举 id / 类名，只需要一个能回答「这块面跟不跟主题」的**行为判据**。

**不用「资源有没有 -night 变体」**（要把同一资源在两个 Configuration 下各解析一次，代价不可接受），
改用**合成后的中性色 + 主题侧亮度**：

```kotlin
ratio = alpha/255 ; base = if (night) 0f else 255f        // 当前主题的页面底色极性
r = (color>>16&0xFF)*ratio + base*(1-ratio)               // g / b 同理
chroma    = max-min  ;  > 24              → 品牌色，出局
luminance = (0.2126r+0.7152g+0.0722b)/255
night → lum ≤ 0.40   ;   day → lum ≥ 0.62 ;   中间带两边都不认（宁可漏不误伤）
```
**半透明必须按主题页面底色合成再判**：`#24FFFFFF` 这类卡底在深浅两个主题下 RGB 都是白，
直接看色值会得出「不跟随主题」的错误结论；合成后叠深色页仍是深色面、叠浅色页仍是浅色面 → 正确。

## 架构盘点：设置卡片「动态 vs 写死」的现状（用户提问后的核实结论）

用户问「系统设置那些 card 是动态适配了还是依旧规则写死」。逐文件核实后结论：
**三条通道并存，两条已动态、一条仍写死，且动态与写死是叠加而非替换。**

| 通道 | 现状 | 具体位置 |
|---|---|---|
| ① 分组卡（MIUIX 列表） | **动态** | 字面名 `installRecycler`/`installPreference` 只是快路径；兜底是 `installDiscoveredDecorations()`：锚点 `DECORATION_ANCHOR_CLASSES = ["miuix.preference.PreferenceFragment"]`（公开名 R8 保留）内部的 `RecyclerView.ItemDecoration` + hook `RecyclerView.addItemDecoration`。裁剪方法按签名找（`clipMethodOf`），不按名字。`routingAvailable = recycler ‖ preference ‖ discovered > 0`（hook:203） |
| ② 独立卡（自绘背景） | **动态 + 设置进程 6 个写死 id** | `standaloneTarget()` 第 843 行 `if (settingsSpecific) knownStandaloneTarget(view)?.let { return it }`；`STANDALONE_CARD_IDS`（hook:1387）= `lock_screen_notification_card`/`float_notification_card`/`show_app_badge_card`/`device_basic_layout`/`device_params`/`view_corner`。**只有 `view_corner` 带真正专属逻辑**（`bluetoothRowOwnsSurface`），其余 5 个就是命中即返回。非集合内 → `CardSurfaceDetector.probe()` 动态；**非设置进程没有 settingsSpecific → 纯动态**（安全中心就靠这条自动生效） |
| ③ 卡片透明度 | **仍完全写死** | `SettingsAppearanceApplier`：`LIGHT_CARD_COLOR_RESOURCES`（15 个写死资源名，:566）+ `isCardLike()`（只看资源名/类名含 "card"，:1258）；`cardFinalDrawableReplacement`（:541）直接 `drawable.mutate().alpha = opacity*255/100` → **「在找其他设置吗」被清空的元凶**。靠 `managesStandalone(view)`（:530/:543）给②让位，但②没接管时会按写死表改 |

**两个关键澄清（写进回答，避免下次重复推导）**
- 通道③ **不是遗留代码**，它是「卡片透明度」这个开关的实现（`APPEARANCE_SLOT_HOME.lightCardOpacity`），
  与「自定义卡片材质」是两个独立功能，只是实现方式是写死资源名表 + 字符串启发式。
- ③ 与①②**不共享信息**：它只认那 15 个资源名，认得的就按 opacity 压 alpha，
  不管这块面是否已被动态通道接管过（只在 `managesStandalone` 为真时让位）。
  所以「动态」体现在**定位与接管**，不体现在**颜色/透明度改写**。

**若要彻底去写死，两个可收点**
1. `LIGHT_CARD_COLOR_RESOURCES` 15 个 → 可并入 `CardSurfaceDetector` 的 SURFACE 档
   （已有「随主题翻转的中性填充色」判据），用动态判定代替资源名表。这是「在找其他设置吗」的正解。
2. `STANDALONE_CARD_IDS` 除 `view_corner` 外的 5 个 → 通用判定现在应已能收，可逐个真机验证后删除，
   只保留 `view_corner` 的蓝牙身份判定（这个是必需的，不能纯动态）。

## 安全中心「卡片没效果」真因：撤销改动后链路断了（用户贴日志定位）

### 根因（三层，按优先级）
1. **最致命：安全中心进程根本没装卡片材质**。撤销改动后，`SettingsCardBackgroundHook.install`

2. **动态 hook 入口绑定错位**：`DynamicCardMaterialHook.install`（`View.onSizeChanged` +

### 菜单弹窗（PopupMenu）漏判根因（本轮结论）

### 关键结论：之前的 PopupWindow 方案完全无效，根因如下
MIUI 的「右上角三点菜单」和「下拉选择框」**都不是 `android.widget.PopupWindow`**，而是 MIUI 自绘组件：
1. **右上角三点菜单** → `miuix.popupwidget.widget.PopupView`（继承 `FrameLayout`）。

1. `hookGlobalActivities()` / `hookInstrumentationLifecycle()` 本就**无条件**对所有被注入进程挂 Activity 生命周期，
   早就具备「全局」能力。唯一阻塞点是 `shouldSkipGlobal()` 末尾的 `return true`。
2. **清底机制已是动态判定，无需新写**：`LayerSession.clearPageSurfaces()` / `isPageSurface()` 靠
   「尺寸占比（w≥72%、h≥32%）+ 正负关键词 + CardView 豁免」判定，对未知包同样工作，
   自带 2500ms rescan 窗口 + OnGlobalLayoutListener(200ms 节流) + `restore()` 还原。
3. **深浅色跟随已是全局的**：`SettingsThemeOverride.resolveMode()` 不做包名过滤（仅 contacts 走专属键），
   通用页面自动跟随深/浅色。

### 改动
- `BackgroundApplier.kt`：`shouldSkipGlobal()` 末尾 → `return !isGenericFullScreenPage(activity)`；
  新增 `isGenericFullScreenPage()`：① lp 宽高均 MATCH_PARENT（浮窗/半透明已被 `isSensitiveTransientWindow` 排除）；
  ② `android.R.id.content` 存在且有 ≥1 个 VISIBLE 子视图。**刻意不卡内容尺寸**——
  onContentChanged 时尺寸还是 0，卡尺寸会让首帧挂不上、退化成 post 补挂而闪。
  六张包名关键词表 + contacts/mms 专属跳过**全部保留**。
- `strings.xml` en/zh：`background_global_summary` →「所有二级页面的背景与颜色」。
